完成 QQ 登录后，下一步是让应用端能调用 Bot，并接收到消息事件。Desktop 中的「连接」配置的是 **OneBot 通信**，它与登录 QQ 用的 WebUI 是两个入口，端口和 Token 也可以不同。

这页先用本机 HTTP 连接查询一次登录信息，再说明应用端一键对接与手动 WebSocket 配置。HTTP 查询成功可以证明接口已通；要自动处理新消息，还需要配置事件接收或 WebSocket。

## 先选连接方式

| Desktop 中的名称 | 谁主动连接谁 | 用来做什么 |
| --- | --- | --- |
| HTTP 服务器 | 应用程序请求 Bot 的 HTTP 端口 | 调用 API，例如查询登录信息、发送消息 |
| HTTP SSE 服务器 | 应用程序连接 Bot 并保持事件流 | 单向接收事件，仅 NapCat 提供 |
| HTTP Webhook | Bot 主动向一个 HTTP URL 发 POST | 向应用程序投递事件 |
| WS 正向服务器 | 应用端主动连接 Bot | 通过 WebSocket 调用 API、接收事件 |
| WS 反向客户端 | Bot 主动连接应用端的 WebSocket 服务 | 应用端提供监听地址，Bot 连接过去 |

正向、反向是从 **Bot 一侧** 命名的。应用端说明里写「反向 WebSocket 服务端」时，Bot 这一侧应选「WS 反向客户端」。不要两边都设成客户端，也不要两边都等别人连进来。

## 先跑通本机 HTTP 查询

本节沿用 [创建第一个 Bot](/docs/first-bot/) 的本机 NapCat。操作前确认 QQ 已登录。示例使用端口 `3000`；如果它已被占用，换一个空闲端口，并同步修改下面的请求地址。

### 1. 添加 HTTP 服务器

1. 打开 Bot 的配置，切到「连接」。
2. 在底部新增工具条选择「HTTP 服务器」。
3. 按下表填写。

| 项目 | 这次使用的值 |
| --- | --- |
| 连接名称 | `local-http`，在这个 Bot 内保持唯一 |
| 消息上报格式 | `Array（结构化数组）`，后续按应用端要求调整 |
| 监听 IP (Host) | `127.0.0.1`，本节只允许同机访问 |
| 端口 | `3000`，或你选定的空闲端口 |
| 监听路径 | `/` |
| 鉴权 Token | 保留新建时生成的随机值，并复制到临时安全位置 |
| 启用此连接 | 开启 |

![Bot 的连接配置：选择连接类型，并填写地址、端口与鉴权信息](/docs/screenshots/bot-connections-light.png)

4. 点击对话框中的「保存连接」。
5. 再点击 **Bot 配置页底部的「保存」**，确认「未保存」提示消失。
6. 按保存结果提示应用改动；如果要求重启，停止并重新启动 Bot，然后确认 QQ 已登录。

「保存连接」把这一条连接放回表单；页面底部的「保存」才提交整份 Bot 配置。这两步不要漏掉。

### 2. 查询登录信息

在当前 Windows 电脑打开 PowerShell，粘贴下面的命令。提示输入 Token 时，粘贴刚才 **OneBot HTTP 连接的鉴权 Token**。

```powershell
$token = Read-Host '粘贴 local-http 连接的鉴权 Token'
$headers = @{ Authorization = "Bearer $token" }
$result = Invoke-RestMethod `
  -Uri 'http://127.0.0.1:3000/get_login_info' `
  -Method Post `
  -Headers $headers `
  -ContentType 'application/json' `
  -Body '{}'
$result | ConvertTo-Json -Depth 5
```

如果你换了端口，也要修改命令里的 `3000`。不要使用 NapCat WebUI 的访问密码替代 OneBot Token。

**完成标志：** 返回内容中 `status` 为 `ok`、`retcode` 为 `0`，`data` 中能看到当前登录账号的信息，例如 `user_id` 与 `nickname`。具体字段以协议端实际返回为准。

这个请求只查询信息，不会发送聊天消息。确认返回的 QQ 号是预期账号，再继续连接应用端。也可以在 Desktop 的 [API 调试台](/docs/debugging/) 完成接口调用与事件检查。

### 3. 请求失败时先检查

| 结果 | 检查顺序 |
| --- | --- |
| 连接被拒绝 | Bot 是否运行、连接是否启用、配置是否保存并生效、端口是否一致 |
| 等待很久后超时 | 地址是否属于同一台主机，监听是否正确，跨机时检查路由和防火墙 |
| 401 / 403 或鉴权失败 | Token 是否完整、是否用错 WebUI 密码、请求头是否带 `Bearer ` 前缀 |
| 地址不存在 / 404 | 当前连接是否真的是 OneBot HTTP 端口，路径是否被改动 |
| 有返回但账号不对 | 是否访问了另一实例的端口，多个 Bot 不能占用相同监听地址与端口 |
| 接口正常但应用不回复 | 继续检查应用端连接、消息事件与插件规则，HTTP 查询本身不会配置这些 |

## 安装在 Desktop 里的应用端，优先使用「对接」

1. 先创建并保存 Bot。新建尚未保存时，「对接应用端」入口不可用。
2. 按 [应用端实例](/docs/apps/) 安装或导入应用框架。
3. 从应用实例卡片或详情打开「对接」，选择刚才的 Bot；也可以从 Bot 的「连接」页进入「对接应用端」。
4. 核对界面给出的连接方向、Bot 主机、应用端主机与端口，确认后保存。
5. 启动应用端和 Bot，检查双方日志。用另一个 QQ 账号向 Bot 发送一条普通消息，确认应用端收到事件。
6. 再按所安装插件的规则测试指令；AI 应用还要先配置模型提供商和凭据。

Desktop 会按框架能力配置正向或反向 WebSocket，支持的跨机组合会使用 SSH 隧道。**Docker 部署的 Bot 目前不支持应用端一键对接**，需要按 [Docker](/docs/docker/) 与应用框架要求手动处理连接。

以 `ncd-app:` 开头的连接由应用端对接管理。需要解绑或更换 Bot 时，从对接入口调整，避免一边手改这条连接、一边又由应用端写回。

## 手动配置正向 WebSocket

适用于应用端明确支持连接 Bot 的 WS 服务端，并且你希望自己管理两侧配置。

1. 在 Bot 的「连接」页新增「WS 正向服务器」。
2. 同机测试时把监听 IP 设为 `127.0.0.1`，端口例如 `3001`，监听路径设为 `/`。
3. 连接角色选择 `Universal（全双工，API + 事件）`。只在应用要求拆分时选 API 或 Event。
4. 保留或设置鉴权 Token，心跳间隔先保持默认 `30000` 毫秒，启用连接。
5. 点击「保存连接」，再保存 Bot 配置，并按提示使配置生效。
6. 在应用端配置 **正向 WS 连接**：地址为 `ws://127.0.0.1:3001/`，Token 与 Bot 一致。
7. 启动应用端，查看连接成功的日志，再发送测试消息。

如果应用端需要特定路径，两侧必须完全一致。`/` 与 `/onebot/v11` 不是同一个地址；不能只看端口相同就认为已配好。

## 手动配置反向 WebSocket

适用于应用端提供 OneBot WebSocket 监听服务，例如应用端说明要求 Bot 连接它给出的 URL。

1. 先在应用端开启对应适配器的 **反向 WS 服务**，记下真实监听地址、端口、路径和 Token。
2. 在 Bot 的「连接」页新增「WS 反向客户端」。
3. 「服务端 WebSocket URL」填应用端给出的完整 URL。假设两者同机，应用监听 `8080` 且路径确实为 `/onebot/v11`，才填写 `ws://127.0.0.1:8080/onebot/v11`。
4. 连接角色按应用要求选择，常见情况为 Universal。心跳默认 `30000` 毫秒，重连默认 `5000` 毫秒；两者都不能低于 `1000` 毫秒。
5. 两侧 Token 保持一致，开启「启用此连接」，保存连接，再保存 Bot 配置。
6. 先确保应用端已监听，再启动或应用 Bot 的连接，查看双方日志。

这里的 `8080` 和路径只是一个条件示例，不代表所有框架都使用这个端口。直接复制别人的地址，是反向连接失败的常见原因。

## 地址、端口与 Token 最容易混淆的地方

| 值 | 正确含义 |
| --- | --- |
| `127.0.0.1` | 当前进程所在机器自己；容器里的它是容器自己 |
| `0.0.0.0` | 监听全部网络接口的写法，不是让另一台机器连接的目标地址 |
| 远端主机地址 | 跨机连接时使用能从连接发起方访问到的地址，或使用 Desktop 支持的 SSH 隧道 |
| WebUI 端口 / 密码 | 登录和管理协议端页面 |
| OneBot 端口 / Token | 应用端收发 API 与事件；每条连接单独配置 |
| HTTP 与 WS | 地址分别使用 `http(s)://` 和 `ws(s)://`，不要混填 |

如果 Bot 和应用端分处两台主机，不要把本机测试中的 `127.0.0.1` 原样抄过去。先画清「谁向谁发起连接」，再从发起方检查目标是否可达。使用 Desktop 对接时，以界面支持的主机组合和隧道方案为准。

新连接默认生成随机 Token。接口一旦允许其他机器访问，保留鉴权，并只开放确实需要的访问范围。Token 只在需要连接的两侧保存，截图、日志和分享的配置要先隐藏它。

## 其他连接选项怎么选

- **消息上报格式**：Array 用结构化消息段，String 用字符串形式。跟应用端适配器要求一致；不确定时先用默认 Array。
- **上报 Bot 自身消息**：需要应用端处理 Bot 自己发出的消息时再开启，并检查插件是否会重复触发。
- **HTTP Webhook**：填写事件接收方真实的 `http://` 或 `https://` URL。SnowLuma 还提供请求超时设置；留空使用引擎默认值。
- **HTTP SSE**：只在 NapCat 下提供，适合需要持续接收单向事件流的客户端。调用 API 是否另配 HTTP，要看客户端的实现。
- **兼任 WebSocket 握手 / CORS / 强制事件推送**：按客户端和协议端需求设置。CORS 是浏览器跨域配置，不能解决端口不通或 Token 错误。
- **调试输出**：排查连接时临时开启，重现问题后查看日志；日志可能包含消息和请求信息，分享前先检查。

监听端口范围为 `1–65535`。同一机器、同一监听地址上的服务不能重复占用相同端口；SSE 与 WS 的新建默认端口都可能是 `3001`，同时建立时要自行区分。

## 在远端 WebUI 改过连接，为什么重启后又变了

Desktop 每次启动远端 Bot，会按自己保存的配置写回远端 OneBot 文件。请在重启前完成同步：

1. 打开这个 Bot 的「配置 → 连接」。
2. 点击底部的「从远端读取」。
3. 核对远端相对 Desktop 多了、少了、改了哪些连接。
4. 确认填入表单，再点击页面底部「保存」。

「从远端读取」面向已保存的远端 Bot；本机 Bot 或尚未保存的新建页面不会提供这个入口。
