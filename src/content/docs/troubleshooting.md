先记住故障停在哪一步：**下载 → 安装 → 进程启动 → QQ 登录 → OneBot 连接 → 应用处理消息**。前一步成功，不代表后一步也成功。把出错的阶段找准，通常比重装全部组件更快。

## 先保存这四条信息

1. Desktop 版本、所用 NapCat / SnowLuma 版本、应用框架版本。
2. 运行位置：本机 Windows、远端 Linux / Windows；原生还是 Docker。
3. 刚才执行的动作，以及界面最先出现的具体错误。
4. 对应时间附近的任务日志、Bot 日志或应用日志。

安装任务失败看「任务」，QQ 启动和协议错误看 Bot 日志，应用报错看应用实例日志，容器退出看 Docker 日志。把这些来源分开，避免拿另一个 Bot 或另一台主机的日志排查。

## 下载慢，或者一直下载失败

### 先确认下载发生在哪里

| 发生位置 | 调整入口 |
| --- | --- |
| Desktop 下载组件、更新包 | 「设置 → 网络」中的代理和对应下载线路 |
| 远端 `curl` / `wget`、系统包管理器 | 远端主机自己的网络配置 |
| Docker 拉取镜像 | 组件页对应的镜像源、远端 Docker 网络 |
| 应用框架安装插件、访问模型服务 | 框架与该实例运行主机自己的配置 |

> **Desktop 的代理不会自动传到 SSH、Docker 或应用框架里。** 详细范围见 [网络设置](/docs/network/)。

### Desktop 下载按这个顺序查

1. 打开「设置 → 网络」，看当前「代理模式」是否与你实际运行的代理软件一致，地址和端口是否正确。
2. 点击「测试连接」检查草稿中的 GitHub API 和下载候选地址。这个测试不保存配置，响应耗时也不等于下载速度。
3. 测试可用后「保存设置」，再发起新的下载。已经开始的请求不会中途切换代理和线路。
4. 固定镜像失败时，换镜像或改回自动选择；固定线路不会自动换站。
5. 看下载进度中的源主机名、速度和换源原因。自动下载可能为避免混用不同文件而重新下载，这不等于缓存损坏。

GitHub API 元数据和安装包下载线路分别配置，给 API 填 PAT 也不能让所有镜像提速。不要把 PAT 发给下载镜像或公开问题。

## 安装任务失败

1. 到「任务」找到那次失败，读出失败阶段：下载、解压、依赖安装还是写入目录。
2. 回「组件」核对选中的主机。远端组件必须装在目标机，本机的同名组件不能替代。
3. 下载失败按上一节处理；缺少系统依赖按组件检测结果补齐；写入失败检查实际目录和执行用户权限。
4. 处理第一条具体错误后，再重新提交一次任务。不要在任务仍运行时重复安装同一个组件。

应用实例安装失败时还要看框架日志、运行时版本与仓库下载。你已经有项目时，可以按 [应用端指南](/docs/apps/) 导入；不要通过新装实例覆盖不明目录。

## Bot 一启动就停止

### 本机或远端原生运行

1. 打开 Bot 日志，找退出前的第一条错误。
2. 检查 QQ、底座和运行时是否都被组件页识别，目录是否属于当前运行主机。
3. Linux 原生检查组件提示缺少的系统库；Windows 远端检查工作进程和目标用户桌面会话。
4. 确认同一个 QQ / Bot 是否已由另一个启动器运行。先弄清原进程归属，再决定停止或重新启动。

远端 Windows 只有服务运行、没有用户桌面时，先修复 [托管会话](/docs/remote-windows/)，不要安装 Linux 的显示环境来解决。

### Docker 运行

打开「容器」，选对应主机，找到容器查看「详情」和「日志」。重点看退出码、是否内存不足终止、端口及挂载。远端终端可做只读检查：

```bash
docker info
docker ps -a --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'
```

`permission denied` 先查 SSH 用户的 Docker 权限；容器退出先查容器日志；已经运行但 QQ 未登录，转到下一节。更多见 [Docker 部署](/docs/docker/)。

## Bot 显示运行中，但 QQ 没上线

运行中只表示进程或容器存在。打开卡片上的 WebUI / 扫码入口，确认 QQ 已完成手机确认，再看协议端是否识别到正确账号。

| 看到的情况 | 先处理什么 |
| --- | --- |
| 二维码过期 | 手动刷新后重新扫码 |
| 手机已扫，界面等待确认 | 到手机 QQ 完成确认，不要连续刷新 |
| SnowLuma 显示「等待 SL 确认」 | QQ 主界面已出现，等待协议端确认状态 |
| 简化扫码取不到图 | 检查桌面 / X11 / AT-SPI / D-Bus，使用 QQ 原窗口或 VNC |
| Windows 远端桌面锁定 | 解锁绑定用户桌面后刷新二维码 |
| WebUI 鉴权失败 | 核对实际配置里的 token / 密码与访问入口 |

NapCat Docker 的有效 token 以当前容器的 `webui.json` 为准，不一定等于创建容器时填过的初始值。更新 Desktop、重新连接后仍失败，检查配置读取权限、限流与两步验证。

SnowLuma 的扫码开关不会自动重启 QQ 或补装依赖。刚打开开关时，按 [扫码指南](/docs/remote-login/) 完成冷启动或使用回退入口。

## QQ 在线，应用端收不到消息

按顺序核对，先让一条连接工作，不要同时新建多条猜测地址的连接。

1. **连接方向正确吗？** 正向 WebSocket 是应用端连接协议端，反向 WebSocket 是协议端连接应用端。把监听地址填到主动连接一侧，往往会连错。
2. **应用端开着吗？** 应用实例是否正在运行，对应 OneBot 适配器是否安装并启用。
3. **地址属于哪台机器？**`127.0.0.1` 永远是当前进程所在机器或容器，不能代表另一台服务器。
4. **端口可到达吗？** 监听 IP、监听端口、Docker 发布端口、主机防火墙和实际访问端口要对应。
5. **token 和路径一致吗？** 检查两边的鉴权与 WebSocket 路径，留意前后空格、大小写和前缀。
6. **双方使用相同的 OneBot 版本和连接角色吗？** API、事件或通用连接的用途不同，事件只到达某一条连接时并不一定能调用 API。
7. **配置保存并加载了吗？** 保存后按提示重启或重连，再看双方日志中是否建立连接。

连接成功后，在 [调试台](/docs/debugging/) 先做一个只读账号信息请求，再给 Bot 发一条测试消息看事件。如果 API 请求能成功而应用没有处理消息，继续查事件连接和应用插件逻辑，不要直接判定 QQ 离线。

### 我在 WebUI 改过，重启又变回来了

Desktop 启动远端 Bot 时会按自己保存的连接重写远端配置。打开 Bot「配置 → 连接 → 从远端读取」，核对差异后保存到 Desktop。只在协议端 WebUI 改，不会自动变成 Desktop 的配置。

## 聊天页或调试台找不到某个 Bot

先确认 Bot 在线、所需 OneBot 连接可用，再检查「设置 → 功能」是否隐藏了对应入口。聊天后台接收、账号用途和账号托盘是各账号单独设置的，打开一个聊天窗口不等于所有账号都启用了后台接收。

聊天媒体加载异常、群文件与导出问题见 [聊天指南](/docs/chat/)；接口参数和事件工作区见 [调试台](/docs/debugging/)。

## SSH 连不上，或重新连接后状态不对

### 连接测试直接失败

1. 核对主机地址与 SSH 端口，确认网络路径、安全组和防火墙允许当前来源。
2. 核对用户名与认证方式。Windows Hello PIN 不是 SSH 密码，密钥认证选的是私钥文件。
3. 首次主机指纹与服务器核对。主机重装或地址复用后指纹变化，应先确认原因。
4. 连接成功后刷新库存，确认目标系统、路径和权限。

### SSH 已恢复，Bot 状态仍未知

先刷新主机与 Bot 状态，查看远端日志确认原进程是否仍在。不要在没有确认时再手工开一份同账号 Bot。Desktop 退出、SSH 断开与远端进程停止不是同一件事。

远端 Windows 还要确认绑定用户是否注销、桌面工作进程是否就绪；Linux 原生则检查实际程序与系统依赖。详见 [Linux](/docs/remote-linux/) 或 [Windows](/docs/remote-windows/) 指南。

## Desktop 退出以后没收到通知

1. 确认 Bot 的「掉线时发送通知」已经开启，通道已测试，设置已保存。
2. 在「设置 → 通知 → 远端脱管监控（NCD Watch）」刷新主机状态，确认安装并同步成功。
3. 普通通知等待 Desktop 心跳过期后才接管，默认 90 秒；Desktop 在线时 `desktop_present_skip=true` 属于正常行为。
4. Linux 上检查服务断开 SSH 后是否仍存在。用户服务被停止时，按 [值守指南](/docs/watch/) 检查 linger。
5. 检查远端能否访问 Webhook / SMTP；互助 Bot 必须同机、在线且连接可用。
6. Docker 检查容器名、执行权限和实际 WebUI 端口，不能只核对一个推算端口。

启用重登二维码时，检查 `capabilities`、`relogin-status` 和服务日志，`once` 不运行重登指令服务。首次等待登录、手动停止、状态未知不会自动发送重登码。不要删除账本来尝试重置，可能造成重复投递。

## 导入配置了，为什么还不能启动

配置包不包含组件程序、插件程序、数据库或系统密钥库。换机后需要先安装相应框架和插件，核对安装路径，再恢复配置；SSH 密码、GitHub Token 等密钥库凭据要重新填写。

到「设置 → 数据」查看：

- **界面偏好待恢复**：点击「重试恢复界面偏好」，不用整包重复导入。
- **框架配置待恢复**：先安装对应实例、停止实例、恢复远端连接，再点击「重试恢复框架配置」。
- **远端身份变化**：主机地址、端口或用户名改过后，先在远端页重新测试连接再恢复。

应用实例档案会保留原主机和安装路径，换电脑不会自动改为新路径。完整范围与恢复步骤见 [备份与迁移](/docs/backup/)。

## 发 Issue 时怎么描述，才方便别人复现

可以复制下面这份模板，填入自己的情况：

```text
Desktop 版本：
底座及版本：NapCat / SnowLuma
应用框架及版本（有关时填写）：
运行环境：本机 Windows / 远端 Linux / 远端 Windows
部署方式：原生 / Docker

我想完成的操作：
1.
2.

预期结果：
实际结果：
第一次出现错误的时间：
已核对的项目：
相关日志：
```

把日志裁到相关时间段，保留原始错误、堆栈和前后必要上下文。遮盖 OneBot token、WebUI 密码、通知地址中的密钥、API Key、SSH 私钥及私人消息；不要贴整个配置 ZIP 或扫码二维码。保留端口、连接类型和经过替换的主机角色，便于判断网络方向。

整理后提交 [GitHub Issue](https://github.com/NapNeko/NapCatQQ-Desktop/issues)。如果只是某一步文档看不懂，也可以给出页面地址和卡住的操作。
