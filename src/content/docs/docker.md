Desktop 的 Docker 部署面向**远端 Linux**。本机 Windows 和远端 Windows 使用原生运行，不要在本机安装 Docker 后寻找同样的部署入口。

如果还没有添加服务器，先完成 [远端 Linux 的 SSH 连接](/docs/remote-linux/)。本页假定测试连接已经成功。

## 1. 在正确的主机上准备 Docker

1. 打开「组件」，切换到准备部署的 Linux 主机。
2. 在运行时依赖中找到 Docker，等待探测结果。
3. 未安装时点击「安装」，按提示提供这台主机所需的提权信息，在「任务」查看进度。
4. 安装完成后重新检测，确认 Docker 已就绪。

侧栏的「容器」只在至少一台远端主机的 Docker 可用时出现；同时要开启「设置 → 功能 → 容器页」。看不到入口时，先检查这两个条件。

Docker 不仅要安装，**登录的 SSH 用户还要能够访问它**。同一 SSH 用户可在远端终端运行下面的只读检查：

```bash
docker info
```

看到服务端信息后继续。如果提示无法连接 Docker daemon，先检查服务；如果提示 `permission denied`，先处理用户权限，不能靠重试拉镜像解决。

需要将用户加入 `docker` 组时，可由服务器管理员执行下面的命令，再退出并重新登录使组权限生效：

```bash
sudo usermod -aG docker "$USER"
```

Docker 组能够控制宿主机容器，请只给你打算用来管理服务器的账户这项权限。

## 2. 拉取协议镜像

1. 保持组件页选中这台 Linux 主机。
2. 找到 NapCat 或 SnowLuma，在对应行点击「拉镜像」。
3. 默认使用界面提供的自动镜像源；某个源不可用时，可以从「选择镜像源」切换。
4. 打开「任务」观察拉取进度，完成后确认镜像已就绪。

这里先准备镜像，不会仅因为拉完镜像就创建一个已经登录的 Bot。容器内依赖由镜像提供，也不用照抄原生部署的宿主机 QQ 依赖清单。

Desktop「设置 → 网络」中的 GitHub / Node.js 下载线路不负责 Docker 拉取。镜像拉取慢时，检查这台 Linux 的网络和此处的镜像源，见 [网络作用范围](/docs/network/)。

## 3. 创建 Docker Bot

1. 到「机器人」新建 Bot，填写 QQ 账号和实例名称。
2. 选择刚才准备镜像的 NapCat 或 SnowLuma 底座。
3. 在「运行场景」选择远程运行，「目标远程主机」选择这台 Linux。
4. 把「启动方式」设为「Docker」，确认界面显示 Docker 与所需镜像已就绪。
5. 保存后，从 Bot 卡片启动。打开日志，等待协议端启动。
6. NapCat 使用 WebUI 完成登录；SnowLuma 使用「扫码登录」或 VNC，要求见 [扫码登录](/docs/remote-login/)。

容器处于运行中、QQ 已登录、OneBot 已连上是三个独立状态，要分别确认。容器没有退出不代表账号已在线。

## 4. 检查端口：区分容器内与宿主机

打开侧栏「容器」（Docker 管理），选择这台主机，在容器卡片查看端口映射；点击「详情」可以看完整端口与挂载。也可以在远端终端运行：

```bash
docker ps -a --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'
```

例如映射显示宿主机 `6388` 转发到容器 `6099`，从宿主机访问时使用 `6388`，在容器内部才使用 `6099`。不要把这个例子当成你的固定端口，以实际映射为准。

| 连接发起方 | `127.0.0.1` 指向哪里 | 应该检查什么 |
| --- | --- | --- |
| Windows 上的 Desktop / 浏览器 | Windows 本机 | 使用 Desktop 提供的入口或对应隧道 |
| Linux 宿主机上的应用 | Linux 宿主机 | 对应容器端口是否发布到宿主机 |
| 同一容器中的进程 | 这个容器 | 协议服务是否监听容器内地址 |
| 另一个容器中的应用 | 另一个容器自己 | 共同网络及实际服务地址，不能用回环代替对方 |

要让宿主机或其他容器访问协议端，容器内服务通常需要监听 `0.0.0.0`，还要配合发布端口或容器网络。服务只监听容器内的 `127.0.0.1` 时，宿主机通过映射也可能访问不到。OneBot 地址、监听方向和 token 继续看 [连接指南](/docs/connections/)。

## NapCat WebUI 提示 token 错误

已有容器的有效 token 以它当前使用的 `webui.json` 为准，最初启动参数中的 token 不一定仍然有效。Desktop 会读取实际配置，鉴权失败后重新核对。

先更新 Desktop 并重新连接 Bot。仍失败时，检查 SSH 用户是否能执行 Docker 命令、读取容器配置，再看 WebUI 是否提示限流或两步验证。不要靠连续尝试大量 token 排查。

## 使用容器页排查

「容器」页按主机展示「容器」「镜像」「网络」「数据卷」，搜索框可按名称、ID 等过滤。操作前先确认选中了哪台服务器。

- **容器**：根据状态启动、停止、暂停、恢复或重启；「日志」读取 `docker logs`，用于确认启动失败位置。
- **详情**：检查退出码、内存不足终止、重启次数、健康检查、网络、端口和挂载。运行时还能查看 CPU、内存及网络、磁盘读写。
- **镜像**：确认所需镜像是否存在，清理前核对引用关系。
- **网络与数据卷**：检查容器使用的网络、持久化位置；仍被容器引用的资源不能直接删除。

删除容器会丢弃它的可写层，挂载的数据卷和宿主机目录保留；删除数据卷会永久删除卷中的内容。配置 ZIP 也不包含容器数据、应用数据库或程序，清理前先确认数据位置并独立备份。

## 启动失败时最有用的三条信息

1. 容器页是否把容器标为退出，退出码是什么。
2. 「日志」末尾的第一条实际错误，而不是最后一行汇总。
3. 实际端口映射和挂载是否符合当前配置。

`内存不足终止：是` 时先处理服务器内存；`permission denied` 时确认执行用户和目录权限；账号未登录则回登录入口处理。不要把所有情况都当作镜像拉取失败。

希望 Desktop 退出后继续监控容器账号，安装 [ncd-watch](/docs/watch/)。它会读取容器状态和 WebUI 账号状态；仅看 `docker ps` 不能判断 QQ 是否掉线。
